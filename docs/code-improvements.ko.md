## 완료한 수정

- 기본 저장소의 작업 전체를 동기화했습니다. MemoryStore는 활성·대기 핸들을
  용량·TTL 퇴거에서 보호합니다. 모든 후보가 사용 중이면 용량은 soft bound이며,
  동시 작업 수는 호스트의 admission control로 제한해야 합니다.
- 초기화 세대로 이전 요청이 지운 SID를 복구하지 못하게 했습니다. SQLite의
  저장·초기화는 로컬 연결 간 원자적 쓰기이며, 이전 세대 요청의 성공 사용량은
  보존합니다. 뒤늦은 최초 생성자의 실패가 다른 요청의 성공 핸들·사용량을
  삭제하지 못하도록 했습니다.
- 비동기 준비·정책 확인·정리를 worker로 옮겼습니다. 일반 취소와 이벤트 루프
  종료 모두 실제 worker 완료까지 lease를 유지합니다. 취소 완료는 동기 작업이
  끝날 때까지 늦어질 수 있고 Python 스레드를 강제 종료하지는 않습니다.
  연속된 검증·준비를 한 worker 작업으로 묶어 왕복 비용도 줄였습니다.
- 인증 marker는 완성된 파일을 원자적으로 공개하며 기존 marker를 덮어쓰지
  않습니다. 프로필 파일시스템은 hard link를 지원해야 합니다. 검증된 환경·인증은
  요청 안에서만 재사용하고 다음 요청에서 경로·파일을 다시 검사합니다. Claude
  사용량 조회의 만료·scope 정보를 보존하고 인증 오류는 서비스 전용 안내를
  유지합니다. 사용량 조회의 인증 누락은 구조화된 상태로 반환합니다.
- 지시문 파일·system prompt가 빈 상태로 바뀐 것도 명시적 reset에 반영합니다.
  해시는 64 KiB 단위로 읽으며 캐시는 동기화된 1,024개 LRU로 제한했습니다.
- Codex의 정상 동기 경로와 비동기·스트리밍 인사말 복구·payload 집계를 맞췄습니다.
  관찰된 사용량·불확실성을 보존하고 도구 실행 뒤 인사말에는 요청을 반복하지
  않습니다. 비동기·스트리밍의 만료·인사말 복구는 공유된 최대 2회 시도이며
  비동기 재귀 복구 순환을 제거했습니다.
- 잘못된 schema·재시도 정의는 모델 실행 전에 거부합니다. enum의 JSON boolean
  비교, fallback 교정 전달, 토큰 합산의 payload·신뢰도·출처 보존을 수정했습니다.
- SQLite 통계는 동일 읽기 snapshot에서 SQL로 집계하며 일치하는 모든 행을
  Python에 가져오지 않습니다. 필터·그룹·빈 값·unknown 의미는 MemoryStore와
  비교하는 회귀 테스트로 확인했습니다.
- 전체 초기화의 조용한 1,000개 제한을 제거했습니다. 추가 메서드
  `ConversationStore.list_all_by_owner()`로 기존 `list_by_owner`의 limit 의미를
  유지합니다. 내부 조회 제한이 있는 custom store는 이 메서드를 구현해야 합니다.

## 책임 분리와 호환성

`ContextSession`을 `context_session.py`로 옮겼으며 이전 package/client import도
유지합니다. provider 생략은 핸들 생성 시 해석합니다. 비동기 refine의 liveness는
worker로 옮겼고 스트리밍 refine은 소비 시 시작하며 조기 종료 시 iterator를 닫습니다.

`planning.py`의 불변 `CallPlan`으로 실행 경로 6곳의 12개 위치 반환값 의존을
제거했습니다. `async_utils.py`는 worker 완료 보호, `store/locking.py`는 저장소
동기화와 요청 예약을 담당합니다. 호출 없는 세션 갱신 helper와 Python SQLite
그룹 집계 경로를 삭제했습니다. `client.py`는 1,889 → 1,767줄로 줄었지만 여전히
큰 조정자입니다. `providers/base.py`와 Claude provider의 전면 분해는 하지 않았습니다.

## 오프라인 성능 근거

동일 Windows 호스트에서 가짜 Claude 응답과 임시 작업 경로를 사용했습니다.
실제 프로세스·모델 호출 없이 warmup 후 40회씩 3묶음의 중앙값입니다. 비교 소스
`5072c53`의 런타임 코드는 `e8300c1`과 같고 수정 후 측정 소스는 `d34f267`입니다.
이후 조회 호환성 변경은 이 측정 경로에 영향을 주지 않습니다. 내부 처리 비용이며
운영 처리량이나 모델 지연 측정이 아닙니다.

| 저장소·인증 | 동기 수정 전 → 후 | 비동기 수정 전 → 후 | 스트리밍 수정 전 → 후 |
| --- | --- | --- | --- |
| Memory·기존 | 0.590 → 0.540 ms | 0.774 → 1.174 ms | 0.920 → 1.449 ms |
| Memory·프로필 | 4.175 → 1.838 ms | 4.075 → 2.238 ms | 4.062 → 2.515 ms |
| SQLite·기존 | 2.235 → 1.804 ms | 2.406 → 3.462 ms | 2.630 → 2.862 ms |
| SQLite·프로필 | 6.960 → 3.242 ms | 8.279 → 4.003 ms | 10.150 → 4.730 ms |

요청별 프로필 검증은 3 → 1회, 안전 경로 검사는 14 → 4회, resolve는 30 → 10회로
줄었습니다. 기존 인증의 비동기 경로에는 worker 왕복·수명 보호 비용이 추가됩니다.
**성능 퇴보가 전혀 없다는 증거는 아닙니다.** 운영 적용 전 동시성·tail latency를
서비스 환경에서 측정해야 합니다.

동일한 10만 행·provider 1개·그룹 없는 SQLite fixture를 tracemalloc과 측정한 결과:
0.583 → 0.0565초, Python peak traced allocation 29.8525 → 0.0047 MiB였습니다.
SQLite 내부 할당은 포함하지 않으며 서로 다른 그룹을 많이 반환하면 결과 메모리도
커집니다. 이 개선을 위해 감사 데이터나 기능을 삭제하지 않았습니다.

## 검증과 남은 작업

추적 파일만 추출한 Windows/Python 3.14 전체 회귀 결과: **1,188개 통과,
39개 건너뜀**. 활성 퇴거·초기화 경쟁·연결 간 원자성·루프 종료·늦은 실패·SQLite
heartbeat·인증 초기화와 snapshot·지시문 제거·provider parity·schema·통계를
검증했습니다. 최종 감사에서 추가로 찾은 세 결함은 수정 후 담당 검토자가 원본
재현을 다시 실행했습니다. 빌드·twine·런타임 의존성 0 검사는 최종 게이트에
포함하며, artifact 버전 0.7.5는 내부 검증용이지 공개 릴리즈 교체가 아닙니다.

남은 작업: 기존 인증의 비동기 오버헤드, 조정자·provider의 추가 분해, MemoryStore
usage 보존 정책과 프로세스 전체 출력 제한. 조용한 잘라내기·삭제는 감사·응답 계약을
바꾸므로 기본값은 변경하지 않았습니다. native schema 교정 feedback은 기존의
명시적 예외이며 라이브러리 전사록 재생 기능을 추가한 것은 아닙니다.
Linux/macOS·실계정·모델·운영 부하·분산 서버 lease는 검증하지 않았습니다.
OS ACL·네이티브 설정 신뢰·동시 작업 제한·서버 간 조정은 호스트 책임입니다.
