# agentcli v0.7.1

[English](v0.7.1.md) | [한국어](v0.7.1.ko.md)

Adds warm (persistent) claude sessions: boot the harness once instead of on
every call.

## Install

GitHub-first release:

```bash
pip install "agentcli-py @ git+https://github.com/saintiron82/agentcli.git@v0.7.1"
```

## Added

- **Warm (persistent) claude sessions (#48).** `claude -p` boots the whole
  harness per call, so even a trivial prompt costs 6–11s. `agentcli.providers.warm`
  opens a claude process once with `--input-format stream-json` and keeps feeding
  it prompts over stdin.

  ```python
  from agentcli.providers.warm import open_warm

  s = await open_warm(append_system_prompt=RULES)
  s.session_id                          # the one thing handed to the caller

  async for chunk in s.stream("question"):    # standard StreamChunk contract
      ...
  text = await s.send("question")             # non-streaming convenience

  await s.send("/clear")                # just a message; session_id changes
  await s.close()                       # `async with` works too
  ```

  Measured on Windows 11 / Claude Code 2.1.220 with lean defaults:

  | Turn | Wall | CLI-reported `duration_ms` |
  |---|---|---|
  | 1 (includes boot) | 6.40s | 1663ms → boot ≈ 4.7s |
  | 2 | 2.69s | 2687ms |
  | 3 | 1.61s | 1611ms |
  | 4 | 1.65s | 1652ms |

  After boot, wall clock ≈ the turn time the CLI reports, so harness overhead is
  effectively zero. TTFT lands at 0.8–1.7s against 6.3–11.1s per call on the
  cold `-p` path.

## Scope

The module opens warm mode and hands over its `session_id`. That is the whole
contract.

Pooling, concurrency distribution, overflow policy, liveness supervision,
automatic restart, restart-time discovery or termination of residual processes,
and any global file or database backing them are the consuming service's job.
agentcli never picks its own storage and never inspects or terminates processes
it does not own. A regression test pins this boundary: the module must not grow
a `WarmPool` / `acquire` / `supervise` / `terminate` / `registry` surface.

A single warm session is **serial** — the next prompt waits for the previous
turn's `result`. Open several sessions if you need parallelism.

Reattaching to a live warm process from a different process is impossible: the
pipes belong to the parent that spawned it and die with it. What you can carry
across processes is the conversation — pass a stored `session_id` as
`resume_session_id`.

Warm mode is claude-only and lives outside the shared provider contract. It is a
separate module rather than a `provider_options` key or a `ProviderCapabilities`
field, so the three-provider normalization contract is untouched.

## Behavior notes

- `--output-format stream-json` requires `--verbose`; the CLI refuses to start
  without it. The module fixes this in argv.
- `/clear` wipes the previous turns without rebooting, but **mints a new
  `session_id`**. Its response body is empty, so if you need to confirm the
  reset, compare `session_id` before and after. Reusing one session across
  unrelated queries without a working `/clear` leaks context between them.
- Context passed via `--append-system-prompt` survives `/clear`, so "keep the
  system and pinned context, drop the previous Q&A" holds within one process.
  It is fixed at boot and cannot change while the session lives.
- `lean` (`--safe-mode --tools ""`) is the default: with tools on, the model
  wanders after `/clear` and per-turn latency rises 3–9×.
- Turn timeouts are bounded. Warm mode is the only spawn path that deliberately
  keeps stdin open — the invariant issue #27 established — so an explicit
  per-turn ceiling stands in for the EOF that normally makes issue #4
  unreachable.

## Verification

- 20 hermetic tests (no claude CLI required) plus end-to-end runs against
  Claude Code 2.1.220.
- Two defects found by a pre-merge review pass and fixed with regression tests:
  - Abandoning a turn mid-stream (a streaming cancel — normal in a chat UI) left
    unread events in stdout, and the **next** turn consumed them as its own
    response while `session_id` stayed stale. Leftovers are now drained; if the
    drain cannot complete, the session is marked unusable and fails loudly
    instead of answering with the wrong turn's content.
  - Concurrent first turns spawned **two** processes because the spawn sat
    outside the lock; the second was unreachable from `close()`. Spawning now
    happens under the lock.
- Sending after `close()` now raises instead of silently spawning a fresh
  process.
