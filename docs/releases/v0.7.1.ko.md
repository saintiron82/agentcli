# agentcli v0.7.1

[English](v0.7.1.md) | [한국어](v0.7.1.ko.md)

상주(warm) claude 세션을 추가한다 — 호출마다가 아니라 한 번만 하네스를 부팅한다.

## 설치

GitHub 우선 릴리즈:

```bash
pip install "agentcli-py @ git+https://github.com/saintiron82/agentcli.git@v0.7.1"
```

## 추가

- **상주(warm) claude 세션 (#48).** `claude -p` 는 호출마다 하네스 전체를
  부팅해 사소한 프롬프트조차 6~11s 가 든다. `agentcli.providers.warm` 은
  `--input-format stream-json` 으로 claude 프로세스를 한 번만 열고 stdin 으로
  프롬프트를 계속 먹인다.

  ```python
  from agentcli.providers.warm import open_warm

  s = await open_warm(append_system_prompt=RULES)
  s.session_id                          # 호출자에게 넘기는 유일한 것

  async for chunk in s.stream("질문"):        # 기존 StreamChunk 계약
      ...
  text = await s.send("질문")                 # 비스트리밍 편의

  await s.send("/clear")                # 그냥 메시지 — session_id 가 바뀐다
  await s.close()                       # `async with` 도 된다
  ```

  Windows 11 / Claude Code 2.1.220, lean 기본값 실측:

  | 턴 | 벽시계 | CLI 보고 `duration_ms` |
  |---|---|---|
  | 1 (부팅 포함) | 6.40s | 1663ms → 부팅 ≈ 4.7s |
  | 2 | 2.69s | 2687ms |
  | 3 | 1.61s | 1611ms |
  | 4 | 1.65s | 1652ms |

  부팅 후에는 벽시계 ≈ CLI 가 보고한 턴 시간이라 하네스 오버헤드가 사실상 0 이다.
  TTFT 는 0.8~1.7s 로, cold `-p` 경로의 호출당 6.3~11.1s 와 대비된다.

## 범위

이 모듈은 상주 모드를 열고 그 `session_id` 를 넘겨준다. 그것이 계약의 전부다.

풀링 · 동시성 배분 · 오버플로 정책 · liveness 감시 · 자동 재기동 · 재기동 시점의
잔여 프로세스 탐색이나 종료, 그리고 그것을 뒷받침하는 전역 파일이나 DB 는 전부
소비하는 서비스의 일이다. agentcli 는 저장소를 스스로 고르지 않고, 자기가 소유하지
않은 프로세스를 조회하거나 종료하지도 않는다. 이 경계는 회귀 테스트로 고정돼 있다 —
모듈에 `WarmPool` / `acquire` / `supervise` / `terminate` / `registry` 표면이
생기면 실패한다.

상주 세션 하나는 **직렬**이다 — 다음 프롬프트는 이전 턴의 `result` 를 기다린다.
병렬이 필요하면 세션을 여러 개 연다.

살아 있는 상주 프로세스에 다른 프로세스가 다시 붙는 것은 불가능하다. 파이프는 그것을
띄운 부모가 소유하고 부모와 함께 죽는다. 프로세스 간에 이어갈 수 있는 것은 대화이며,
저장해 둔 `session_id` 를 `resume_session_id` 로 넘기면 된다.

상주 모드는 claude 전용이고 공유 프로바이더 계약 밖에 있다. `provider_options` 키나
`ProviderCapabilities` 필드가 아니라 별도 모듈이므로 3-프로바이더 정규화 계약은
그대로다.

## 동작상 유의점

- `--output-format stream-json` 은 `--verbose` 를 요구한다. 없으면 CLI 가 기동을
  거부하므로 모듈이 argv 에서 고정한다.
- `/clear` 는 재부팅 없이 이전 턴들을 지우지만 **새 `session_id` 를 발급**한다.
  응답 본문이 비어 있으므로 리셋을 확인하려면 전후 `session_id` 를 비교한다. 한
  세션을 서로 무관한 질의들에 돌려 쓰는데 `/clear` 가 먹지 않으면 질의 간에
  컨텍스트가 샌다.
- `--append-system-prompt` 로 넣은 컨텍스트는 `/clear` 를 살아남는다. 따라서
  "시스템·고정 컨텍스트는 유지하고 직전 Q&A 는 버린다" 가 한 프로세스에서 성립한다.
  기동 시 고정이라 세션이 사는 동안에는 바꿀 수 없다.
- `lean`(`--safe-mode --tools ""`) 이 기본값이다. tools 를 켜면 `/clear` 이후
  모델이 툴로 헤매 턴당 지연이 3~9배로 뛴다.
- 턴 타임아웃에 상한이 있다. 상주 모드는 stdin 을 의도적으로 열어두는 유일한 spawn
  경로 — issue #27 이 세운 불변식을 깨는 자리 — 이므로, 평소 issue #4 를 도달
  불가능하게 만들어 주던 EOF 대신 명시적인 턴별 상한을 둔다.

## 검증

- hermetic 테스트 20개(claude CLI 불필요)와 Claude Code 2.1.220 대상 end-to-end
  실행.
- 머지 전 리뷰에서 결함 2건을 찾아 회귀 테스트와 함께 고쳤다:
  - 턴을 스트리밍 도중 포기하면(챗 UI 에서 정상인 스트리밍 취소) 읽지 않은 이벤트가
    stdout 에 남고 **다음** 턴이 그것을 자기 응답으로 소비했다. `session_id` 도 낡은
    값에 고착했다. 이제 잔여를 배수하고, 배수를 끝내지 못하면 세션을 사용 불가로
    표시해 조용히 엉뚱한 턴의 내용을 답하는 대신 명시적으로 실패한다.
  - 첫 턴을 동시에 호출하면 spawn 이 락 밖에 있어 프로세스가 **2개** 떴고, 두 번째는
    `close()` 로 닿을 수 없었다. 이제 spawn 이 락 안에서 일어난다.
- `close()` 이후 전송은 조용히 새 프로세스를 띄우지 않고 예외를 낸다.
